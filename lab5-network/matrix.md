Источник фактов — чарт `lab3-platform/helm/shop` и код `lab3-platform/src`.
Модель: default-deny в обе стороны (ingress и egress) для всех подов `shop`.

## Инфраструктура

Без этих потоков default-deny ломает не приложение, а то, что за ним следит и им управляет.

| откуда                         | куда                     | порт       | зачем                                              |
|--------------------------------|--------------------------|------------|----------------------------------------------------|
| prometheus (ns `monitoring`)   | api, worker, batch       | `http` (8080 / 8081 / 8080) | ServiceMonitor скрейпит `/metrics` у всех трёх |
| cnpg-operator (ns `cnpg-system`) | postgres               | 8000       | статус инстанса; без него Cluster уходит в неизвестное состояние |
| postgres (instance manager)    | kube-apiserver           | 6443       | instance manager внутри пода базы сам ходит в API  |
| kubelet (identity `host`)      | все поды                 | порты проб | Cilium пускает трафик с ноды по умолчанию (`allow-localhost`), отдельного правила не нужно |

Метрики самой базы (порт 9187) сейчас никто не скрейпит: `PodMonitor` в кластере нет.
Если включить `enablePodMonitor` у CNPG, default-deny срежет этот поток молча — понадобится
отдельное правило `prometheus → postgres:9187`.

Репликация между подами базы не нужна при `instances: 1`. При росте до двух
понадобится разрешение `postgres ↔ postgres` на 5432.

## Почему так

- **У api и worker один исходящий поток — в базу.** Других обращений по сети в коде
  нет: ни трейсинга, ни вызовов между сервисами. api → worker не нужен: worker
  берёт заказы из postgres.
- **batch вообще ни с кем не говорит.** В чарте у него нет `DATABASE_URL`, в коде
  он не открывает `store`. Это Deployment, а не CronJob, и сеть ему нужна только
  для того, чтобы его скрейпил prometheus. Поэтому у batch закрыт даже DNS.
- **DNS нужен api и worker**: строка подключения из секрета CNPG содержит имя
  `shop-db-rw.shop.svc`. postgres по имени никуда не ходит: instance manager
  обращается к API по `KUBERNETES_SERVICE_HOST`, а это IP.
- **Внешний мир закрыт всем.** Приложению наружу ходить незачем.
- **Посторонний** обязан нести `app.kubernetes.io/name` и `part-of`, иначе Kyverno
  (`require-labels`) его не впустит. Поэтому он помечен `part-of=shop` и отличается
  только `name`. Тест специально бьёт в эту ловушку: политика, выбирающая
  источники по `part-of=shop`, его пропустит. Разрешения надо выдавать по
  `app.kubernetes.io/name`. DNS у постороннего открыт, чтобы `connection refused`
  или таймаут не путались с `could not resolve`: проверяем запрет к сервису, а не
  поломку DNS.

## Что это значит для Части 4

1. **Каждая ✅ — два правила**: egress у источника и ingress у получателя.
   api → postgres = egress у api на :5432 + ingress у postgres от api.
2. **Вход k6 нельзя описать селектором подов.** k6 стучится в NodePort с хоста.
   В Cilium такой трафик приходит с identity `world`, а если бэкенд на другой ноде и
   источник прошёл через SNAT — `remote-node`; при локальном бэкенде и kube-proxy
   в режиме iptables — `host`. Открыть :8080 «для всех» нельзя: тогда пройдёт и
   посторонний. Нужны `fromEntities` в CiliumNetworkPolicy. Стандартная
   NetworkPolicy так различать не умеет: её `ipBlock` в Cilium не покрывает ноды
   кластера.
3. **Egress postgres → kube-apiserver** — та же история: в Cilium это entity
   `kube-apiserver`, а `ipBlock` на адрес ноды её не поймает.
4. Итог: точечные разрешения внутри `shop` — стандартная NetworkPolicy, а вход
   снаружи и API-сервер — CiliumNetworkPolicy. Если писать только стандартные
   политики, ломаются именно эти два места, и ломаются молча.

## Что это значит для Части 5

Каждая ячейка таблицы «Приложение» — тест-кейс пробника. Ожидаемое значение берётся
отсюда, фактическое — из прогона. Пробник в `shop` проходит те же политики Kyverno:
метки, пробы, разрешённый реестр.

Отдельный тест-кейс сверх таблицы: посторонний под стучится не в ClusterIP, а в
`<IP ноды>:30006`. После SNAT его трафик приходит в api как нода, то есть
совпадает с разрешением для `remote-node`. Если обход сработает — это честный
результат, а не провал работы.

## Осталось проверить на живом кластере

- Порт статуса CNPG (8000) и обращение instance manager к API подтвердить на версии
  оператора, которая стоит в `cnpg-system`. Если без DNS у postgres что-то
  отвалится, это всплывёт в Части 5, а не в проде.
- Какой identity Hubble покажет у запроса k6 (`world`, `remote-node` или `host`).
