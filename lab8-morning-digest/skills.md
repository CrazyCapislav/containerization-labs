# AI skills: know-how агентов сводки по релизу

Документ описывает, **что именно умеют агенты** воркфлоу `Кварт: сводка по релизу`: в каком порядке они действуют, по каким правилам и чего им не доверено вовсе.

Главный принцип, к которому я пришёл не сразу: **модели оставлено только суждение, а решения и побочные эффекты вынесены в обычные узлы.** Причина не идеологическая, а измеренная, и разобрана в [`README.md`](README.md), Шаги с 5 по 7. Коротко: запрет в системном промпте модель читает как пожелание, а не как ограничение.

---

## Toolkit

Три инструмента, все через MCP, **по одному на агента**. Выбрать не тот инструмент агент физически не может, потому что выбора у него нет.

| Инструмент | MCP-сервер | Что делает | Что принимает на вход | Чей |
|---|---|---|---|---|
| `read_text_file` | filesystem | Читает текстовый файл из примонтированного каталога `/workspace`. Выйти за пределы каталога сервер не даёт, он проверяет это сам | `path` обязателен; необязательные `head` и `tail` читают первые или последние N строк | Агент А: шаблон release notes |
| `get_file_contents` | github | Читает файл из репозитория на GitHub | `owner` и `repo` обязательны; `path` путь внутри репозитория, `ref` необязателен и по умолчанию ветка по умолчанию | Агент Б: чек-лист выкатки |
| `add_issue_comment` | github | Добавляет комментарий к существующей задаче | `owner`, `repo`, `issue_number` обязательны; `body` текст комментария | Агент В: отметка о повторной сборке |

<details><summary><b>Примечание: почему инструментов три, а не пять</b></summary>

Сервер filesystem отдаёт 14 инструментов, сервер GitHub отдаёт 29. Узел `MCP Client Tool` в n8n умеет их фильтровать (`include: selected`), и агенту уходят только перечисленные. Это не косметика: схемы инструментов целиком попадают во **входной** контекст и переотправляются с каждым обращением к модели. Три схемы стоят примерно 290 токенов на запрос, сорок три не оставили бы места под сами данные.

Из набора сознательно убраны четыре инструмента, бывшие в ранних версиях:

| Инструмент | Почему убран |
|---|---|
| `write_file` | Документ не должен ехать внутри JSON-аргумента вызова: модель обрывала содержимое на полуслове и обрыва не замечала |
| `issue_write` | То же самое, в худшем виде: поле `body` то обрывалось, то отсутствовало в вызове целиком |
| `list_issues` | Поиск дубликата перестал быть работой модели и стал работой обычного HTTP-узла |
| `issue_read` | Прочитав комментарии, модель брала оттуда `comment_id` и подставляла его в `add_issue_comment`, где это поле означает реакцию. Сервер отбивал вызов |

Последняя строка про важное: лишний контекст навредил так же, как недостаток. Модель заполняет соседние поля схемы тем, что попалось под руку.

</details>

## Skill 1. Сводка по релизу (агент А)

**Задача:** превратить список коммитов между двумя тегами в release notes, которые дежурный прочитает перед выкаткой.

### Порядок действий

1. Прочитать шаблон: `read_text_file` с путём из поля `templatePath` задания. Шаблон задаёт обязательные разделы и их порядок.
2. Разложить коммиты по разделам.
3. Ответить **полным текстом сводки и ничем больше**: без предисловий, без пояснений, без упоминания самого факта работы. Ответ целиком попадает в файл.

### Правила

- Разделы ровно как в шаблоне: все четыре, в том же порядке, с теми же заголовками. Пустой раздел не выбрасывается, а помечается строкой «изменений нет», потому что дежурный должен видеть разницу между «ничего не было» и «не проверяли».
- Раздел «Требует внимания дежурного»: **не больше пяти пунктов**, каждый одной строкой. При избытке приоритет у миграций, оплаты и заказов.
- В пункте всегда два элемента: что меняется и **почему это риск**. Без второго пункт бесполезен.
- Ссылка строится как `https://github.com/OWNER/REPO/commit/SHA`, где `SHA` берётся из поля `sha` **того же** коммита. Перепутанная ссылка хуже отсутствующей: дежурный пойдёт смотреть не тот диф.
- Раздел «Что увидят клиенты и курьеры» пишется человеческим языком, без имён файлов и путей.
- Объём сводки от 700 до 1100 символов.
- Писать сразу набело, черновиков не делать.

### Чего агент А не решает

- **Что считать риском.** Признаки риска расставлены детерминированно, до обращения к модели, по путям изменённых файлов. Агент получает готовое поле `risk` с метками и решает только, что из размеченного важно дежурному и как это сформулировать.
- **Куда и когда писать файл.** Агент отдаёт текст, файл кладёт обычный узел и тут же проверяет результат на диске.

<details><summary><b>Примечание: почему разметка риска не доверена модели</b></summary>

Проверка «лежит ли файл в `db/migrations`» детерминирована. Отдавать её модели означало бы платить токенами за то, что надёжно считается кодом, и получать разброс от прогона к прогону. Критерии риска:

| Метка | Условие |
|---|---|
| `миграция` | есть файл в `db/migrations` |
| `оплата-заказы` | есть файл в `services/payments` или `services/orders` |
| `откат-хотфикс` | в сообщении коммита встречается «откат» или «хотфикс» |
| `конфигурация-выкатки` | есть файл в `.github/workflows` или `deploy/` |

Критерий «коммит затронул больше N файлов» рассматривался и был отклонён: размер дифа не говорит о риске, большой рефакторинг тестов безопаснее однострочной правки таймаута в оплате.

Пути файлов после разметки в полезную нагрузку **не попадают**: они уже не нужны, а весили примерно половину всего списка коммитов. Из 18 коммитов размечено 11, итоговая нагрузка 1838 символов.

</details>

## Skill 2. Тело задачи по чек-листу (агент Б)

**Задача:** собрать тело задачи, в котором чек-лист выкатки дополнен тем, что стало критичным именно в этом релизе.

### Порядок действий

1. `get_file_contents` с `owner`, `repo` и `path` из задания: это чек-лист выкатки. Он живёт в репозитории и правится командой через пул-реквесты, поэтому берётся оттуда, а не из памяти модели и не из копии на стенде.
2. Выдать **готовое тело задачи и ничего больше**: ни предисловий, ни пояснений, ни упоминания того, что оно собрано. Ответ целиком станет телом задачи.

### Правила

- Чек-лист воспроизводится **целиком**, со всеми пунктами и их нумерацией. Это обязательства команды, сокращать их нельзя.
- Вводная часть чек-листа (абзац до первого заголовка) не переписывается, текст начинается сразу с раздела «До выкатки».
- Под пунктами, которые стали критичны из-за рискованных изменений этого релиза, добавляется строка «важно в этом релизе: ...» с объяснением, что именно изменилось и чем это грозит.
- Пункты, которых релиз не касается, остаются как есть, без приписок.
- На русском, объём от 900 до 1200 символов.
- Писать сразу набело.

### Чего агент Б не решает

- **Создавать задачу или нет.** Это решает узел ветвления по полю `duplicate`. Агент Б запускается только тогда, когда задачи по этому тегу ещё нет, и про существование дубликатов вообще не знает.
- **Саму запись.** Задачу создаёт обычный HTTP-узел из текста, который подготовил агент. До записи текст проверяется: длина, целый хвост и число пунктов чек-листа в сравнении с эталоном.

## Skill 3. Отметка в существующей задаче (агент В)

**Задача:** если задача по этому релизу уже есть, не создавать вторую, а оставить в существующей короткую отметку о повторной сборке.

### Порядок действий

1. `add_issue_comment` ровно с четырьмя полями: `owner`, `repo`, `issue_number` из задания и `body` с текстом комментария.
2. Ответить одной строкой: номер задачи.

### Правила

- Комментарий на русском, **не длиннее 300 символов**.
- По существу: релиз пересобран, **не больше трёх** самых важных рисков, что проверить дежурному. Перечислять всё не надо.
- Новую задачу не создавать и существующую не закрывать: у агента есть только комментарий.
- Поля `comment_id` и `reaction` не трогать.

<details><summary><b>Примечание: почему комментарий такой короткий</b></summary>

Первая версия разрешала 600 символов, и модель оборвала аргумент на полуслове: комментарий закончился на `(9) Feature flag new_checkout`, причём вызов инструмента модель посчитала успешным. Длина аргумента и надёжность его доставки связаны напрямую, поэтому ограничение в 300 символов и «не больше трёх рисков» это не стилистика, а защита от обрыва. После ограничения пять прогонов подряд дали целые комментарии длиной от 232 до 288 символов.

</details>

## Общие правила, за которыми следят узлы, а не агенты

Это тот слой, который делает воркфлоу пригодным к эксплуатации. Каждое правило появилось после наблюдаемого отказа.

| Правило | Почему не доверено модели |
|---|---|
| Задача по релизу создаётся **один раз** на тег | Агент при `duplicate: true` создал задачу, а потом сам написал в ответе: «Я ошибся, задачу создавать нельзя». Запрет в промпте не остановил вызов инструмента |
| Каноничной считается **самая старая** совпавшая задача | GitHub отдаёт задачи от новых к старым, и выбор «первой совпавшей» был произвольным |
| Сводка считается сданной только после **проверки файла на диске** | Агент дважды отчитался успехом, не записав файл. Проверяется существование файла, его размер и возраст |
| Тело задачи проверяется **до** создания и **после** | Созданную задачу нельзя отозвать программно. До записи сверяется длина, хвост и число пунктов с эталоном, после записи то, что вернул GitHub |
| Комментарий **вычитывается и проверяется на обрыв** | Обрыв аргумента выглядит как текст, оборванный на полуслове, при успешном статусе вызова |
| Цикл инструментов у каждого агента ограничен сверху (`maxIterations`) | Модель не выходит из цикла сама: после записи файла шла перечитывать шаблон |
| Потолок вывода выставлен по измеренной потребности каждого агента | Groq проверяет лимит по **ожидаемому** выводу, который оценивает из `maxTokensToSample`. Общий потолок на всех означал, что агент резервирует в несколько раз больше, чем тратит |

Сверка по `state=all` при поиске дубликата сделана намеренно: тег не переиспользуется, поэтому **закрытая** задача на тот же тег тоже значит «релиз уже разбирали».
